Product & engineering scope · Hood — Borrow

Best-rate borrow, across protocols and chains

Status: draft for engineering scoping · Data snapshot: rates pulled live 2026-09-24, ETH spot ≈ $2,677 (Binance ETHUSDT). Every rate in this document is real, pulled from each protocol's own public API at write time — re-pull before shipping, rates move daily.

1TL;DR

Hood's Borrow panel already does something clever: given a collateral asset, it checks Aave v3 across every EVM chain Aave is deployed on and routes the user to whichever chain nets the best supply-minus-borrow rate, bridging there first via the existing NEAR Intents (Aurora) integration if needed. That's implemented today in src/Borrow.jsx.

This document scopes the next step: shop rates across protocols, not just across chains of one protocol — Aave, Compound v3, Spark, and Morpho Blue. (Kamino is addressed separately in §4 — it's Solana-only, which changes the architecture entirely.)

User holds 1 ETH on Base and wants USDC. Instead of naively supplying ETH and borrowing USDC on Base's Aave market, the product checks Aave / Compound / Spark / Morpho across Base, Arbitrum, and Ethereum, computes the net cost of borrowing — not just the raw borrow rate, see §5 — and either keeps the user on Base or routes them through a bridge to wherever the net cost is genuinely lowest, but only if the saving clears the cost of moving.

Headline finding

The worked simulation in §8 uses today's real numbers and reaches a non-obvious conclusion: for a 1 ETH position, the "obviously best" cross-chain route is not worth it once bridging and gas costs are netted out — and one of the four protocols (Morpho Blue) is quietly the worst option today despite a competitive headline borrow rate, purely because of how it pays (or doesn't pay) yield on collateral. That distinction is the entire reason this needs careful engineering rather than "find the lowest borrow APY."

2The use case, restated precisely

A user holds an asset (ETH) on one chain (Base) and wants liquidity in another asset (USDC) — without selling the ETH (no taxable event in many jurisdictions, no giving up upside exposure). The system should:

  1. Query supply APY for the collateral (ETH) and borrow APY for the target asset (USDC) across every supported protocol × chain combination.
  2. Compute the net annual cost of borrowing at a safe LTV for each combination (§5 explains why raw APY comparison is wrong).
  3. Rank them, weighing the one-time cost of getting there (bridge fee + destination gas) against the annualized saving.
  4. If a different protocol/chain wins net of moving costs: bridge ETH there, supply it as collateral, borrow USDC there, then bridge the borrowed USDC back to the chain the user wanted it on. If nothing beats staying put, execute locally and skip the bridge — the optimizer must be willing to say "do nothing."

Why someone wants this (real use cases)

  • Hedging a position — a user long ETH who's nervous about a near-term drop can borrow USDC against it as a partial hedge, instead of selling into weakness and re-buying later.
  • Spending without selling — Hood already has a crypto card (src/Card.jsx, src/lib/immersve.js). Borrowing USDC to fund card spend keeps the ETH position intact — the single biggest reason people borrow against crypto instead of just swapping.
  • Bridging cash flow — "I get paid next week but need $2k now": borrow against ETH you don't want to touch, repay from the next paycheck, no forced sale at a bad moment.
  • Airdrop / point farming — some protocols reward borrowers and suppliers with points or tokens for TVL (Morpho's MORPHO, Compound's COMP, historically Aave's Merit program). A user may want exposure to a specific protocol's incentive program even where the raw net-cost math doesn't fully justify it — surface this as its own line item (§10), never blended into the headline APY.

3What's already built

Baseline to extend, not replace:

  • src/Borrow.jsx already queries Aave v3's public GraphQL API (api.v3.aave.com/graphql) across every EVM chain in AAVE_CHAINS (Ethereum, Base, BNB Chain, Polygon, Optimism, Arbitrum, Monad).
  • Already computes a net cost metric, not a raw APY comparison: netCostApy(rate) = ASSUMED_LTV * borrowApy - collateralAsset.supplyApy (ASSUMED_LTV = 0.65), sorting chains by that.
  • Already applies a safety haircut: safeBorrowAmount = maxBorrowAmount * 0.85 — 85% of the maximum borrowable amount, not a health-factor target per se (§6 explains why that should change).
  • Already executes cross-chain moves via NEAR Intents / Aurora's 1-click swap API (AURORA_QUOTE_URL / AURORA_DEPOSIT_SUBMIT_URL / AURORA_STATUS_URL in src/lib/shared.js) — quote → deposit → poll status.
  • Does not yet support any protocol other than Aave, repayment, withdrawal/unwind, or reward claiming.

This scope adds: Compound v3, Spark, and Morpho Blue as additional rate sources under the same net-cost ranking; repayment; unwind/withdraw; reward claiming; a real health-factor target in place of the flat 85%-of-max heuristic; and — the biggest addition — Intents Connect, which changes what the execution orchestrator in §12 even needs to build.

Why this matters for this scope

Intents Connect's /api/v1/executions/{wallet}/steps endpoint accepts an array of up to 30 chained EVM steps (to, value, functionSignature, parameters) in one signed intent — and Aurora's own documentation explicitly names this exact pattern as supported: “sequential destination-chain actions like collateral supply followed by borrowing.” Concretely, the whole “bridge ETH → approve → supply as collateral → borrow USDC” sequence in §11 could be one Intents Connect execution, not four separately-orchestrated transactions we build and babysit ourselves.

How it works (non-custodial): the user signs one bounded intent (source chain/asset/amount, destination chain/target protocol, max fee, allowed execution path, deadline, nonce). An intermediary account on the destination chain — controlled via NEAR's Chain Signature (MPC), not custodied by Aurora — executes exactly that authorized sequence and nothing else. Execution is tracked through explicit states: CREATED → DEPOSIT_PENDING → DEPOSIT_PROCESSING → OPERATION_PENDING → OPERATION_PROCESSING → SUCCESS. On failure (gas spike, protocol pause, etc.) the reason is surfaced to the UI and recovery paths are available for every failure state — real, built-in retry/resume semantics we wouldn't have to invent ourselves.

Chain coverage confirmed direct from their docs: Base, Arbitrum, and Ethereum are all listed “✓ Supported” as both source and destination — exactly the three chains this scope needs.

Still needs a build-time check
  • Whether access is self-serve or gated — their docs point to a “Get access” step and contact@aurora.dev, which could be a lead-time item.
  • Fee structure for Intents Connect specifically (not fully surfaced in this pass).
  • Whether a real chained “supply then borrow” example exists today or only single-action ones — confirm with an actual dry-run ("dry": true) before relying on it.

Recommendation: prototype the exact “bridge ETH from Base → supply on target protocol → borrow USDC” sequence as one Intents Connect steps-execution dry-run early in implementation. If it works as documented, it replaces most of §12's execution-orchestrator task with an integration, not a from-scratch multi-chain state machine.

5Why "lowest borrow rate" is the wrong metric

The naive approach — find the protocol with the lowest USDC borrow APY — is wrong for two reasons the existing Aave-only code already gets right, and this expansion must preserve:

  1. The collateral itself may or may not earn yield, and that has to be netted against the borrow cost. Aave / Compound (base-asset side) / Spark pay yield on supplied collateral; Morpho Blue's isolated markets structurally do not. Ignoring this makes Morpho look artificially competitive on a raw-APY comparison when it isn't, once netted — see §8's real numbers.
  2. LTV/LLTV differs by protocol (80% on Aave, 86% on this Morpho market) — a protocol that lets you borrow more against the same collateral changes the absolute dollar cost/benefit even at an identical APY, so any comparison must fix a target LTV and compare every option at that same target, not each protocol's own max.

Formula

Extend the existing netCostApy:

net_annual_cost(protocol, chain) =
  (collateral_value_usd × target_ltv × borrow_apy)
  − (collateral_value_usd × collateral_supply_apy)              // 0 for Morpho-style isolated markets
  − (collateral_value_usd × target_ltv × reward_apy_on_borrow)  // incentive tokens, priced conservatively
  + (collateral_value_usd × reward_apy_on_supply)               // e.g. Aave Merit-style incentives, if any

Rank every protocol × chain combination by this number (lower is better) — not by raw borrow APY. Price reward APYs at a conservative discount (e.g. 50%) to spot, since incentive programs change or end without notice and the token itself may be illiquid; show reward-inclusive and base-rate numbers as two separate figures in the UI.

6Health factor — what to actually target

The current safeBorrowAmount = maxBorrowAmount * 0.85 is a reasonable rough margin but isn't expressed in the industry-standard unit — Health Factor (HF) — which is what every protocol's own tooling, alerts, and the user's mental model already use:

HF = (collateral_value_usd × liquidation_threshold) / borrowed_value_usd

Aave/Spark call this "liquidation threshold"; Morpho Blue's equivalent is the market's LLTV directly — Morpho doesn't separate max-LTV from liquidation-LTV the way Aave does, LLTV is the liquidation threshold.

Recommendation
  • On open, target HF ≈ 1.8–2.0. Meaningfully more conservative than 85%-of-max, which on an 80%-max-LTV asset with an ~83% liquidation threshold often works out to an HF near 1.15–1.2 — uncomfortably tight for a position nobody actively watches. ETH can move 20%+ in a day.
  • Monitor continuously. Warn at HF < 1.4; treat HF < 1.15 as urgent (repay-or-add-collateral prompt). Don't build auto-deleveraging into v1 without an explicit opt-in and its own security review — moving funds without a fresh signature each time is exactly the class of risk flagged in §13.
  • Recompute HF per protocol correctly: Aave/Spark expose healthFactor directly; Compound v3 exposes isLiquidatable(account) plus balances (compute HF manually); Morpho Blue: HF = collateral_amount × oracle_price × LLTV / borrowed_amount.
  • Because a position on a chain the user isn't actively watching is a small risk multiplier of its own, require a larger net benefit before recommending a cross-chain move than a same-chain protocol switch — e.g. the annualized saving should clear the moving cost by 3–5×, not just any positive margin.

7Repayment flow

Not implemented yet — full scope for this addition:

  1. Partial or full repayment, from either the origin chain or the chain the debt actually sits on. Same-chain: approve + repay (Compound v3 models this as a supply of the base asset). Cross-chain: bridge the repayment amount first (same NEAR Intents flow), then repay — quote the bridge fee up front.
  2. Interest accrual between quote and execution: debt grows every block. Either overpay slightly (e.g. +0.5%) and refund the dust, or query exact current debt right before submitting and use type(uint256).max for the approval — the standard "repay full balance" pattern across Aave/Compound/Morpho.
  3. Full close-out: after full repayment, withdraw collateral. Moving it back to the user's original chain is a second bridge leg — quote this too, since for a fully-closed small position it can be a meaningful fraction of any yield earned over the position's life.
  4. UI must show, before confirming: current debt, interest accrued since last update, bridge cost, and (if closing) withdrawal + bridge-back cost — the same "show total cost before committing" principle as opening.

What this actually shows
  1. Morpho's zero collateral yield makes it the worst of the four, despite a lower headline borrow rate (4.84% vs Aave Base's 4.97%) — exactly the failure mode §5 warns about. A naive "lowest borrow rate wins" ranking would have picked the worst option on the table.
  2. Arbitrum is strictly worse than Base right now on both legs — no reason to move there today, contradicting the intuition that Arbitrum/Morpho would be the winner. Rates move daily; this is why ranking has to be computed live, never assumed.
  3. Ethereum mainnet Aave has the best raw net cost — a $9.75/yr improvement over Base. But moving 1 ETH collateral to L1 (plus later moving USDC back) means one or two L1-touching legs; at typical gas conditions a supply+borrow pair on Ethereum plus the initial bridge fee plausibly costs $15–$60+ — which can exceed the entire annual saving being chased. This is the concrete case for the "require 3–5× the moving cost" rule in §6.
  4. Net-net for this exact snapshot: staying on Base is the right call, or at most a same-L2 comparison (which today still favors Base). The product should be able to answer "no move is worth it right now," not just always route somewhere.

Regenerate this table with live numbers as part of building the rate-aggregation service — treat the figures above as proof the model produces a real, checkable, non-obvious answer, not as a table to hardcode.

10Claiming incentive rewards

  • Morpho — MORPHO incentives on many markets, distributed off-chain and claimed via Merkl (api.merkl.xyz): fetch the user's claimable proof, submit it to Merkl's on-chain distributor. Confirm current API paths at build time — Merkl's API has evolved.
  • Compound v3 — native COMP rewards on some Comet deployments via the CometRewards contract's getRewardOwed / claim — fully on-chain, no external indexer needed.
  • Aave — has run various programs (stkAAVE emissions historically, "Merit" more recently on specific markets), claimable through Aave's rewards controller. Check per-market — the rewardTokens field in DefiLlama's pool data is a quick signal.
  • Spark — has distributed SPK incentives on specific markets — check current program status/contract at build time.

Surface "+ X% in token rewards (est.)" as a clearly separated second line under the base APY, never blended into the headline number, and build a periodic job per protocol so the user sees unclaimed amounts without checking each protocol's own site.

12Developer task breakdown

  1. Rate aggregation service — generalize the existing Aave-only fetch into a protocol-agnostic adapter interface (getSupplyApy, getBorrowApy, getMaxLtvOrLltv, getRewardApy); one implementation per protocol.
  2. Net-cost ranking engine — implement the §5 formula against the adapter output; unit-test against the §8 numbers as a golden-value check.
  3. Route planner — stay-vs-move decision using the §6 threshold rule; a full cost preview (bridge fee, destination gas, net annual benefit) before any transaction is signed.
  4. Execution orchestrator — per §3a, prototype this as an Intents Connect steps-execution first (chaining approve + supply + borrow as one signed intent) rather than a bespoke multi-chain state machine — their docs name this exact pattern as supported, and failure/recovery is already built in. Only fall back to a self-built approve → bridge → supply → borrow → bridge-back state machine if a dry-run shows the steps API can't actually do it for our specific protocol calls.
  5. Health factor monitor — background job recomputing HF per open position per protocol's own formula, alerting at the two thresholds.
  6. Repayment + unwind flow — per §7, both same-chain and cross-chain paths, full-balance-safe repay pattern.
  7. Reward claim job — per §10, one job per protocol with an active incentive program, surfaced as its own UI line.

13Open questions for the team

Needs a decision before build
  • Kamino/Solana — separate scope item, or not at all for v1? Recommend: not for v1 (see §4).
  • Auto-rebalancing — should an open position ever move to a newer better-rate opportunity automatically, or only on open? Rebalancing carries the same bridge/gas cost as opening, so needs the same 3–5× threshold — and doing it automatically means holding some standing authorization to move user funds without a fresh signature each time, which is a custody question, not just an engineering one.
  • Custody model for repeated actions — does every step (bridge / supply / borrow / repay / claim) require a fresh wallet signature (safest, most friction), or does the product hold a session key / smart-account permission for the multi-step flow (smoother, meaningfully larger attack surface if that key is ever compromised)? Intents Connect's own model (§3a) is a reasonable default for the open/bridge leg — one bounded signature per execution, non-custodial intermediary, no standing key — but ongoing health-factor monitoring or auto-rebalancing still need their own answer. Worth solving once, consistently — this is the same class of question flagged for the Last Dance game's real-money plan.
  • Intents Connect access — confirm whether API access is self-serve or requires reaching out (contact@aurora.dev) before counting on it for the execution orchestrator — could be a lead-time item, not just an integration task.
  • Audit posture — Aave v3, Compound v3, Spark, and Morpho Blue are all long-running, heavily audited, blue-chip protocols with real TVL; base protocol risk here is about as low as DeFi lending gets. The residual risk is almost entirely in this product's own orchestration code (approvals, the multi-step state machine, bridge integration) — that's what actually needs a security review before real funds flow through it.
